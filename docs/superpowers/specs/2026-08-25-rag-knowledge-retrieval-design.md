# RAG 知识库检索注入方案设计

> 状态：待评审 · 日期：2026-08-25 · 本期只出方案，不写代码
> 关联知识源：`Markdown/kb.md`（唯一知识源）

## 目标

将 AI 助手的知识库接入方式从"整库全量注入"升级为"按问题检索注入"：

1. 知识库全面覆盖（9 个产品 + 后台 + 小程序 + 通用平台，17 大章节、~70 小节）也能用——每次请求只注入与用户问题最相关的 3~5 个片段，控制 token 成本与响应速度。
2. AI 能"识别"知识库：通过 system 指令 + 注入片段自带的来源标注，让模型清楚何时应以知识库为准、何时应如实说明无信息。
3. 主/备用三条通道行为一致，前端无需改动（`injectKnowledge: true` 已固定传递）。

## 现状与问题

- **现状**：`functions/api/chat.js`、`workers/index.js`、`netlify/functions/chat.js` 三处逻辑相同——`injectKnowledge === true` 时把整个 `Markdown/knowledge-base.md`（旧版，约 6KB，仅覆盖 2 个产品）拼接进 system prompt。
- **新版知识库**：`Markdown/kb.md` 正文约 34K 字符（≈ 2.5 万+ tokens），若继续全量注入：
  - 每次请求输入 token 巨大 → 首字响应变慢、免费档成本浪费；
  - 已有 6 条上下文裁剪 + 思考模式（max_tokens 翻倍），长对话易顶满上下文；
  - 无关内容稀释注意力（"大海捞针"效应），回答质量反而下降。

结论：必须做检索（RAG），不能整库塞。

## 已确认的决策

| 决策点 | 结论 |
|---|---|
| 检索方案 | 方案 A：关键词/混合检索（零依赖、内存打分、毫秒级） |
| 意图门控 | 方案 C：复用前端既有意图体系做门控 + 打分阈值兜底 |
| 知识源 | `kb.md` 为唯一知识源；`knowledge-base.md` 保留在仓库但不再被引用 |
| 改动范围 | 主通道 `functions/api/chat.js` + 备用通道 `workers/index.js`、`netlify/functions/chat.js` 三处同步 |

## 总体架构与数据流

```
用户消息
  └─> 意图门控（寒暄快速跳过；KB 相关意图关键词命中则必检）
        └─> 切块检索：bigram 相似度 + 关键词命中 + 标题加权 打分
              ├─ 最高分 < 阈值 → 不注入（视为与知识库无关）
              └─ top-K 片段 → 拼入 system prompt（带【来源】标注）
                    └─> 请求 SiliconFlow → 流式/非流式回答
```

- 检索在函数内存中完成，无外部 API、无数据库依赖；单次检索开销微秒~毫秒级。
- 流式与非流式共用同一注入代码路径（注入发生在构建 requestBody 之前）。

## 模块设计

### 1. 知识库加载与缓存

- **Pages Functions / Worker**：沿用现有 `fetch('/Markdown/kb.md')` 运行时读取 + 进程内缓存（`cache: 'no-store'` 下仅缓存成功结果）。
- **Netlify Functions**：沿用现有 `fs.readFileSync` 多候选路径探测 + 带 TTL 的模块级缓存。
- 三处统一将文件路径抽成配置常量（见第 6 节），默认指向 `Markdown/kb.md`。

### 2. 切块（buildChunks）

规则：

- 按行扫描，以 `^## ` 和 `^### ` 标题行为切块边界；块 = 标题行 + 其下正文，直到下一个同/更高级标题。
- 跳过 `## 目录` 章节；文件头部标题 + 用途说明 blockquote 保留为前置块（块 0，供兜底注入）。
- 块内保留原始 Markdown（表格、列表原样），但剔除 `---` 分隔线空行。
- 大块保护：块正文 > 1500 字符时按空行二次切分，仍超长按行切（Markdown 表格无空行，必须兜底）。
- 实测产出：**77 块**、平均 310 字符、最大 1083 字符（未触发大块保护）。

块结构（内部表示）：

```js
{ id: 12, headingPath: '九、产品六：个人精英健康Pro+测评系统 > 9.3 五大测评项目', title: '9.3 五大测评项目', text: '<块正文>' }
```

### 3. 检索打分（scoreChunk）

中文无空格，采用"字符 bigram + 词元"混合分词：

- **分词**：查询与块文本都生成字符相邻二元组（bigram）；英文单词、数字、型号（如 `LT-BBSSP`、`BBS-ROOM`）按词保留。
- **打分公式**（已实测验证）：
  - `score = 0.65·queryCoverage + 0.35·Dice + 标题命中加成`；
  - `queryCoverage = 查询词元命中数 / 查询词元总数`——覆盖率主导，避免短查询（如"睡眠"）被块长度稀释到阈值以下；
  - Dice 为辅助分；标题命中（产品名/章节名在标题）额外加 `0.25·标题命中率`。
- 取分数最高的 top-K（默认 4）块；最高分低于阈值 `minScore`（**实测定稿 0.18**）视为无相关知识 → 不注入。
- 实测参考：单字查询"睡眠"命中 0.9+；"睡眠监测仪怎么连蓝牙？"命中该产品章节 4 块（0.41~0.48）；"你好/今天天气/谢谢"全部 0 命中不注入。

### 4. 门控（gate）

门控完全由"寒暄词表跳过 + 打分阈值"实现，不再额外维护意图关键词表：

- **寒暄快速跳过**：消息等于寒暄词表中一词（你好/谢谢/再见/哈哈/好的 等）或长度 < 2 字符 → 跳过检索，直接对话。
- **阈值兜底**：非寒暄消息一律执行检索，以打分阈值 `minScore=0.18`（第 3 节）为准——分数低于阈值视为与知识库无关，不注入。这是"意图门控"的实际实现：阈值本身即门控，无阈值即无关。
- **追问兜底**：最后一条用户消息 ≤8 字符或无命中时，合并"上一条用户消息 + 本条"重新检索（实测"那血氧呢？"→ 正确回溯到睡眠监测仪章节），解决指代追问丢上下文的问题；全程基于请求内消息历史，**无跨用户状态**。
- **产品清单兜底**：泛化"有什么产品/有哪些产品/介绍一下"类问题对"产品体系总览"表格块召回弱，识别到后无论关键词命中强弱，都把"产品体系总览"块置顶注入（实测已生效）。

### 5. 注入格式

在现有 system prompt 追加位置改为追加检索结果段：

```
--- 产品知识库（检索自《kb.md》）---

【来源：九、产品六：个人精英健康Pro+测评系统 > 9.3 五大测评项目】
<块正文>

【来源：五、产品二：睡眠呼吸监测仪（五人系统） > 5.3 功能说明】
<块正文>

--- 使用说明 ---
1. 仅当问题涉及公司/产品/设备/操作/后台/小程序等业务范畴时，优先依据上方片段回答；
2. 片段未覆盖的内容，如实说明"知识库中暂无相关信息"，不得编造型号、参数或操作步骤；
3. 与业务无关的问题（闲聊、通用知识）按常识回答，不要提及知识库。
```

若检索无命中（最高分低于阈值），则不追加任何知识库段，保持原 system prompt 原样——这是与现状最不同的行为：模型不再"被迫"看整库。

### 6. 配置项

每处函数文件顶部定义常量（env 可覆盖，缺省用默认值）：

```js
const KB_CONFIG = {
  sourcePath: '/Markdown/kb.md', // Netlify 形态为相对仓库根路径
  topK: 4,           // 注入片段数
  minScore: 0.18,    // 注入阈值（实测调优定稿）
  enabled: true      // 总开关（false 时行为退回现状：不注入）
};
```

> 配置集中定义在共享模块 `shared/kb-retrieval.js` 的 `KB_CONFIG_DEFAULTS` 中，三通道默认一致（代码内常量，无需环境变量）。

### 7. 容错与降级

- 知识库读取失败 → 跳过注入，正常对话（与现状一致），`console.warn` 记录。
- 无片段超过阈值 → 不注入（不降级为全量，避免退回高成本路径）。
- 产品清单兜底（见第 4 节）：泛化清单问题即使关键词命中弱，也强制注入总览块。
- 检索代码异常（理论上不应发生，防御性 try/catch）→ 不注入，不影响主流程。
- 流式 / 非流式 / 识图路径：识图（`image`）请求不做知识库注入（现状即如此），文本对话两条路径共用注入逻辑。

## 风险体检与应对（上线前核查结论）

| # | 潜在问题 / 后续场景 | 应对（已实现或已确认） |
|---|---|---|
| R1 | **追问/指代丢上下文**："那蓝牙呢？""它多少钱"无关键词 | 短消息（≤8 字符）或无命中时合并上一条用户消息重试检索；基于请求内历史，无跨用户状态 |
| R2 | **短查询被块长度稀释**："睡眠"两字打分过低 | 打分改 `queryCoverage` 主导（实测 0.9+ 命中），Dice 仅作辅助 |
| R3 | **目录章节污染打分**（罗列全部产品名） | 切块时整章跳过 `## 目录`（实测已跳过） |
| R4 | **三处通道代码漂移** | 抽取共享模块 `shared/kb-retrieval.js`（CJS，require/import 双兼容），三通道只做"加载 + 注入" |
| R5 | **部署依赖：新知识库未提交 git** | ⚠️ `Markdown/kb.md` 当前未跟踪，**上线前必须提交**，否则部署后读不到 |
| R6 | **中文文件名 URL 编码**（Pages fetch） | `new URL` 自动百分号编码，Pages 静态服务按 UTF-8 解码；部署后 curl 验证 200 |
| R7 | **同义改写召回不足**（"晚上老醒"→睡眠监测） | 阈值偏保守（0.18）宁可多注入不漏；预留同义词映射与向量升级路径 |
| R8 | **无命中时模型凭记忆瞎答** | 注入段使用说明强制："片段未覆盖如实说明、建议联系客服、不得编造" |

| R10 | **阈值凭感觉拍脑袋** | 独立脚本 `scripts/test-kb-retrieval.js` 用真实知识库实测 13 个用例后定稿 0.18 |
| R11 | **泛化"有什么产品"问题召回弱** | 产品清单模式兜底：强制注入"产品体系总览"块（实测置顶 1.000） |

## 升级路径（向量语义检索，本期不做）

检索函数抽成单一入口（如 `retrieve(query, chunks)`），为向量方案留替换位：

1. 离线脚本 `scripts/build-kb-index.js`（Node）：调用 SiliconFlow `BAAI/bge-m3` embedding，为每块生成向量，输出 `Markdown/kb-vectors.json` 提交仓库；
2. 运行时：查询经同一 embedding API 向量化（每次请求 +1 次 API 调用），余弦相似度取 top-N；
3. 混合模式：向量 top-N ∪ 关键词 top-M，去重合并后注入；
4. 触发条件：关键词检索在真实使用中召回不足（如同义改写问题频繁漏命中）时再启用。

## 开放项（上线后跟进）

1. `topK=4`、`minScore=0.18` 已按实测定稿；若线上出现漏召回（日志 `[KB-RAG] no hit` 且用户问题明显属于业务范畴），再下调 minScore 或增加同义词映射。
2. 若出现专名召回缺口，增加同义词映射（如 `ROOM` → `导航ROOM系统`、`生命潮` → `生命潮®`）。
3. 前端 `config/ai-chat-config.js` 的 intentClassification 仅用于 temperature/maxTokens 策略，与检索门控无关；若将来需要前端 intent 参与门控，再另行设计。
4. 上线后关注：`[KB-RAG] hits:` 日志中的命中来源与分数，用于持续调优阈值与发现召回盲区。
